并发抢票系统 · 架构图解

一段 Lua，扛住 7000 并发

用户请求只访问 Redis，一次 Lua 脚本原子完成判单；支付与入库全部交给 RabbitMQ 异步，最终落入 PostgreSQL。正确性靠状态机与多级幂等，可靠性靠三层防御。

01 / 07 · 系统总览

系统总览

三段式：Redis 前置拦截 + MQ 异步解耦 + DB 最终落盘。热路径唯一操作是一个 Lua 脚本，全程不碰数据库。

    U["客户端 · 7000+ 并发"] -->|"POST /reserve"| H["Gin Handler"]

    subgraph GO["Go 服务"]
        H --> RW["ReservationWorkflow"]
        PW["PaymentWorkflow"]
        OW["OrderWorkflow"]
        RC["ReconcileWorkflow"]
    end

    RW -->|"Lua 原子判单"| REDIS[("Redis · 唯一判单源")]

    subgraph MQ["RabbitMQ"]
        QPAY["支付队列"]
        QDELAY["延时队列 · TTL 15min"]
        QTO["超时队列"]
        QORD["入库队列"]
    end

    RW -->|"即时支付消息"| QPAY
    RW -->|"延时消息"| QDELAY
    QDELAY -->|"过期 → 死信"| QTO
    QPAY --> PW
    QTO --> PW
    PW -->|"MarkPaid"| REDIS
    PW -->|"入库消息"| QORD
    QORD --> OW
    OW -->|"GORM 事务"| PG[("PostgreSQL")]
    RC -.->|"每分钟对账"| REDIS
    RC -.->|"补写落库"| PG
面试要点订票请求同步返回，支付/超时/入库全部异步；MQ 同时投递「即时支付」与「15 分钟超时」两条消息，超时消息过期后经死信交换进入超时队列。

02 / 07 · 订单状态机

订单状态机

支付与超时两个 Lua 脚本都以 status == RESERVED 为前置条件——并发到达时先到者赢，状态单向流转不可逆。

stateDiagram-v2
    [*] --> RESERVED : Lua 原子创建
    RESERVED --> PAID : 支付成功 · MarkPaid
    RESERVED --> TIMEOUT : 15min 超时 · MarkTimeout
    PAID --> [*] : 异步写 PostgreSQL
    TIMEOUT --> [*] : 回滚库存 · 释放购买资格
面试要点「支付成功」与「超时取消」并发到达是秒杀系统的经典竞态；状态前置校验保证只有先到者能翻转，绝不会出现「库存已回滚、订单却已支付」。

03 / 07 · Lua 原子判单

Lua 原子判单

一个脚本在 Redis 单线程上原子完成 6 步。7000 并发打到同一个 key 也是串行判单——不需要分布式锁，也不需要数据库行锁。

flowchart TB
    subgraph REQ["7000 并发请求"]
        U1["用户 A"]
        U2["用户 B"]
        U3["用户 C …"]
    end

    subgraph LUA["Redis 单线程 · 一个 Lua 脚本原子执行 6 步"]
        direction TB
        S1["① 查已订 · GET ordered"]
        S2["② 查余票 · GET remain"]
        S3["③ 扣库存 · DECR remain"]
        S4["④ 生成订单号 · INCR seq"]
        S5["⑤ 写订单 · HSET reservation"]
        S6["⑥ 标记已订 · SET ordered"]
        S1 --> S2 --> S3 --> S4 --> S5 --> S6
    end

    REQ --> LUA
    S6 -->|"返回 订单号 / 售罄 / 已订"| RES["立即响应 · 零 DB 访问"]
面试要点6 步合并在一次原子执行里，中间不会暴露「读到有余票、写入时已无票」的中间态；热路径零 DB 访问，是本机 QPS 2 万的根本原因。

04 / 07 · 三层可靠投递

三层可靠投递

每一层有自己的失败模式，所以不能只靠一层；而每一层的设计又倒逼出下一层的需求。

flowchart TB
    subgraph L1["第一层 · 预防 —— 让失败可感知、可撤销"]
        C1["消息发送失败"] --> M1["confirm + Lua 原子回滚"]
    end
    subgraph L2["第二层 · 遏制 —— 让失败不扩散"]
        C2["消费失败 · 重复投递"] --> M2["幂等消费 + 有限重试 + 停车场"]
    end
    subgraph L3["第三层 · 兜底 —— 让漏网之鱼自愈"]
        C3["消息彻底丢失 · MQ 故障"] --> M3["定时对账 · 不走 MQ"]
    end
    L1 -->|"防不住"| L2 -->|"防不住"| L3
面试要点预防：publisher confirm 让发送失败可感知，失败即 Lua 原子回滚（删单·还票·释放资格）。遏制：at-least-once 下幂等是消费者的义务，坏消息有限重试后进停车场。兜底：独立于 MQ 的定时对账，扫 Redis 补写/超时，自愈到最终一致。

05 / 07 · 重试拓扑

RabbitMQ 重试拓扑

坏消息不无限 requeue：走 retry 队列 TTL 退避，broker 自动维护的 x-death 计数满 3 次进停车场。

flowchart LR
    MAIN["主队列 main"] -->|"Nack · 未满 3 次"| RX["Retry 交换机"]
    RX --> RQ["Retry 队列 · TTL 10s"]
    RQ -->|"过期 → 死信"| MAIN
    MAIN -->|"x-death 已满 3 次"| PARK["停车场队列 · 人工处理"]
面试要点TTL 天然就是退避；x-death 是 broker 写进消息头的死信历史（零额外状态）。该拓扑对支付/超时/入库三条队列都生效，坏消息既不空转、也不丢失。

06 / 07 · 分层架构

分层架构

domain 不感知 MQ（纯业务、可单测），workflow 组合 domain + MQ 做异步编排。实线 = 调用，虚线 = 依赖注入装配。

flowchart TB
    H["handler"] --> W["workflow · 编排 MQ"]
    W --> D["domain · 纯业务"]
    D --> R["repository"]
    R --> M["model"]

    A["app · 依赖注入"] -.->|装配| W
    A -.->|装配| D

    W -->|MQ 消息| MQ[("RabbitMQ")]
    D -->|Lua 原子| CACHE[("Redis")]
    R -->|GORM 事务| DB[("PostgreSQL")]
面试要点把核心一致性逻辑（Lua、GORM 事务）放进 domain，与 MQ 解耦，可脱离消息队列单独理解与测试；workflow 只负责编排收发。
